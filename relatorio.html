Relatório Técnico

Sistema de Gerenciamento de Inscrições em Eventos Acadêmicos
Disciplina: Estrutura de Dados — Universidade Estadual do Ceará (UECE)
Professor: Bonfim Amaro Junior  ·  2026.2

1. Problema

A UECE realizará uma semana acadêmica com palestras, oficinas e minicursos. Cada atividade possui um código único, um título e uma capacidade limitada. Estudantes podem se inscrever em uma ou mais atividades. Havendo vaga, a inscrição é confirmada; caso contrário, o estudante entra em uma fila de espera FIFO, respeitando a ordem de chegada.

Quando uma inscrição confirmada é cancelada, a vaga liberada é ocupada automaticamente pelo primeiro da fila. Quando a capacidade de uma atividade aumenta, vários estudantes são transferidos da fila para a lista de inscritos, preservando a política FIFO. O objetivo é um programa de terminal em C11, com TADs e alocação dinâmica, avaliado pela correção das estruturas e de sua integração.

2. Arquitetura dos TADs

O sistema é decomposto em cinco TADs, cada um com interface (.h) e implementação (.c) separadas: Atividade, ABB, Lista (inscritos), Fila (espera) e Histórico.

2.1 Atividade

typedef struct Atividade {
    int codigo;
    char titulo[100];
    int capacidade;
    int qtdInscritos;
    int qtdEspera;
    Lista inscritos;   /* lista de inscritos */
    Fila  espera;      /* fila de espera   */
} Atividade;

O código é um inteiro positivo único. Cada nó da ABB guarda uma referência a uma Atividade, que por sua vez contém sua lista e sua fila. Os contadores qtdInscritos e qtdEspera espelham o número real de nós de cada estrutura.

2.2 Lista de inscritos

typedef struct NoInscrito {
    int matricula;
    char nome[100];
    struct NoInscrito *prox;
} NoInscrito;

typedef struct Lista {
    NoInscrito *inicio;
    NoInscrito *fim;
} Lista;

Lista simplesmente encadeada com ponteiros de início e fim. Novas inscrições e promoções entram sempre no fim (O(1)). A remoção por matrícula percorre a lista e trata explicitamente a remoção do primeiro, de um elemento intermediário e do último; ao remover o último, o ponteiro fim é reajustado para o nó anterior (ou NULL), nunca apontando para memória liberada.

2.3 Fila de espera

typedef struct NoEspera {
    int matricula;
    char nome[100];
    struct NoEspera *prox;
} NoEspera;

typedef struct Fila {
    NoEspera *inicio;
    NoEspera *fim;
} Fila;

Fila FIFO encadeada com enfileirar no fim e desenfileirar do início, ambos O(1). Além disso, permite cancelar uma reserva em qualquer posição (início, meio ou fim) preservando a ordem relativa dos demais, apenas religando os ponteiros.

2.4 Árvore Binária de Busca (ABB)

typedef struct NoABB {
    Atividade *atividade;
    struct NoABB *esq;
    struct NoABB *dir;
} NoABB;

Indexada pelo código da atividade: inserção sem duplicados, busca por código, percurso em ordem crescente, contagem de nós e cálculo de altura (altura −1 para árvore vazia, 0 para uma árvore com apenas a raiz). A remoção de atividades não é exigida e não foi implementada.

2.5 Histórico

typedef struct Evento {
    int seq;
    char tipo[32];
    int codigo;
    int matricula;
    struct Evento *prox;
} Evento;

typedef struct Historico {
    Evento *inicio;
    Evento *fim;
} Historico;

Lista global encadeada com início e fim, registrando em ordem cronológica os eventos CADASTRO, INSCRICAO, ENTRADA_ESPERA, CANCEL_INSCRICAO, CANCEL_ESPERA, PROMOCAO e AUMENTO_CAPACIDADE. Cada evento armazena cópia dos valores, não ponteiros para nós que possam ser removidos. A sequência começa em 1 e incrementa a cada registro.

Cada atividade é um nó da ABB; dentro dela, a lista de inscritos e a fila de espera são encadeadas e independentes. Uma mesma matrícula pode estar em atividades diferentes, mas nunca duas vezes na mesma atividade (nem uma na lista e outra na fila).

4. Fluxo de inscrição e cancelamento

4.1 Inscrição (INSCRIVER)

  1. Localizar a atividade na ABB (erro ATIVIDADE_INEXISTENTE se ausente).
  2. Verificar se a matrícula já está na lista ou na fila (erro ALUNO_DUPLICADO).
  3. Se qtdInscritos < capacidade: inserir no fim da lista, incrementar o contador e registrar INSCRICAO.
  4. Caso contrário: enfileirar no fim, incrementar o contador de espera e registrar ENTRADA_ESPERA, informando a posição na fila.

4.2 Cancelamento de inscrito (CANCELAR)

  1. Remover o nó da lista em qualquer posição e decrementar o contador.
  2. Registrar CANCEL_INSCRICAO.
  3. Se houver espera, desenfileirar o primeiro, inseri-lo no fim da lista e registrar PROMOCAO (logo após o cancelamento).

4.3 Cancelamento na espera (CANCELAR)

Remover a reserva da fila mesmo no meio, sem promoção (não havia vaga ocupada), e registrar CANCEL_ESPERA. Matrícula ausente nas duas estruturas produz ALUNO_NAO_ENCONTRADO sem alterar o estado.

4.4 Aumento de capacidade (AUMENTAR)

  1. Somar o incremento positivo d à capacidade.
  2. Registrar AUMENTO_CAPACIDADE.
  3. Promover do início da fila enquanto houver vaga e espera, registrando um PROMOCAO por aluno, em ordem FIFO.

5. Invariantes preservadas

  • 0 ≤ qtdInscritos ≤ capacidade — só se inscreve/promove quando há vaga.
  • Contadores espelham os nós reais — todo incremento/decremento acompanha uma inserção/remoção.
  • Matrícula nunca nas duas estruturas — duplicidade verificada em ambas antes de inserir.
  • Ordem FIFO — enfileira no fim, desenfileira do início; cancelamento no meio apenas religa ponteiros.
  • Sem vaga ociosa com espera — toda liberação de vaga promove imediatamente enquanto houver fila.
  • Eventos íntegros após liberação — o histórico guarda cópias, não ponteiros.
  • Operação inválida não altera estado — validação antes de qualquer mutação; consultas não mutam.

6. Complexidades

OperaçãoCusto esperado

Verificação de aluno duplicadoO(I + E)
Cancelamento por matrículaO(I + E) no pior caso
Promoção de um aluno (início da fila)O(1)

A é o número de atividades, I o de inscritos e E o de estudantes na espera de uma atividade. A hipótese de árvore degenerada (inserções em ordem crescente ou decrescente) leva a busca/inserção a O(A); em árvore equilibrada, O(log A).

8. Limitações conhecidas

  • Título e nome são armazenados como palavra única sem espaços (underscore permitido), conforme o contrato.
  • Remoção de atividades da ABB não é implementada (opcional na especificação).
  • A ABB não é balanceada: em inserções ordenadas degenera para O(A).
  • Linhas de entrada limitadas a 4095 caracteres; contadores em int.

10. Declaração de uso de IA

Foi utilizado um assistente de IA (LLM) como ferramenta de apoio no desenvolvimento. Dois exemplos de sugestões aproveitadas ou corrigidas:

  • Aproveitada — na promoção em lote do comando AUMENTAR, coletar as matrículas promovidas em um vetor temporário para imprimir a linha OK AUMENTAR antes das linhas PROMOVIDO, respeitando a ordem de saída exigida pelo contrato.
  • Corrigida — o ajuste do ponteiro fim ao remover o último nó da lista/fila (fim = anterior), evitando ponteiro pendente para memória liberada; o primeiro esboço não tratava esse caso de forma segura.

A utilização de IA não implicou penalidade; a correção do programa, dos testes e do relatório permanece de responsabilidade da equipe.
